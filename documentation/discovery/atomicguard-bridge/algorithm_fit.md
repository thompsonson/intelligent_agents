# Algorithm Fit: Bridging `discovery/` and `atomicguard`

## Purpose

`environment_design.md` specifies `StatefulDiscoveryNode`/`StatefulDiscoveryEnvironment`'s shape; `scenario.md` specifies the concrete fixture-backed topology. Neither answers the question this document exists to answer: does `discovery.agents.discovery_agent.DiscoveryAgent` - the DFS-with-retrace-plus-readiness-sweep algorithm `backtracking-exploration/algorithm_fit.md` and `and-joins/algorithm_fit.md` derived and proved - actually still fit, once the environment underneath it is genuinely real instead of a frozen dataclass? This should have been argued before implementation, the way every other step's `algorithm_fit.md` was written first; it wasn't, and this document is that argument written after the fact, plus what it surfaces as still open.

## Does the algorithm need to change? No - and here's why that's not just an assertion

`DiscoveryAgent.walk()`'s only environment dependencies are `sense_edges(node_id)`, `sense_requires(node_id)`, `get_move_cost(from_id, to_id)` - three method calls, nothing else. Nothing in the DFS-with-retrace exploration phase, the LIFO parent stack, or the readiness sweep's route-replay logic inspects *how* those three methods produce their answers. The algorithm's correctness arguments (`backtracking-exploration/algorithm_fit.md`'s full-exploration/bounded-moves result, `and-joins/algorithm_fit.md`'s termination argument) are proofs about the *sequence of calls* `walk()` makes and how it reacts to their return values - they never depended on `sense_edges()` being a free field read. That's what makes "run `DiscoveryAgent` completely unmodified against real, subprocess-backed nodes" a meaningful claim to test rather than a foregone conclusion: the algorithm's proofs, read carefully, never used the thing that changed.

`tests/test_discovery_agent_integration.py` is that claim tested, not just argued: both environments' walks produce identical `DiscoveryWalkResult`s (`path`, `nodes_sensed`, `total_cost`, `blocked_nodes`, `goal_reached`) over the identical topology, ungated and gated.

## Sensing has real cost now - and the algorithm's discipline around that turned out to matter for real

`discovery/`'s own `sense()` closure inside `walk()` already never re-senses a node once it's in `known_edges` - a discipline that cost nothing to get right when sensing was a free field read, so nothing ever tested whether it actually mattered. It does now: `sense_edges()` is a real subprocess round-trip through `DualStateAgent`. `DiscoveryAgent.walk()` itself has always respected this (it's the reason `nodes_sensed` can be smaller than `len(path)` at all, since step 2), so the algorithm didn't need to change here either - but `real_discovery/atomicguard_backed/visualization/discovery_view.py`'s *first* version didn't inherit that discipline, and paid for it: `build_networkx_graph(env)` re-sensed every node in `env.nodes` on every single frame render, 90 real subprocess calls for a 15-frame/6-node walk that needed only 6 (caught in PR #15's review, fixed by threading `_walk_frames()`'s own already-sensed data through instead of reading the environment directly - and the same bug, cost aside, turned out to be present in `discovery/`'s own visualization too, see [`../experiments/04_real_discovery_bridge.md`](../experiments/04_real_discovery_bridge.md) for the full account).

The lesson worth keeping, stated as an algorithm-fit property rather than just a bug-fix note: **anything that touches this environment needs to inherit `walk()`'s own "never re-sense a known node" discipline explicitly** - it's not free anymore, and nothing about a working test suite guarantees a caller (like a visualization) actually got it right, since a re-sense produces the *same, correct* answer either way. Only the real cost tells you it happened.

## What a failing sense means for the walk - open, untested

`AtomicGuardCheckEnvironment.check_invariant()` catches `RmaxExhausted` and turns it into a plain `bool` - a failing check is a valid, expected answer. `sense_edges()` has no equivalent valid-but-negative answer: there's no meaningful empty-tuple-vs-exception distinction for "the check that would have told us what this node notifies never produced one." So `sense_edges()` lets `RmaxExhausted` propagate uncaught, straight up through `DiscoveryAgent.walk()`'s `sense()` closure - which has no `try`/`except` anywhere around it, so a real failure crashes the entire walk, not just the one node.

Untested by this experiment (every fixture check is a trivial `cat`, which never fails) - and genuinely open what the *right* behavior is, not just what happens today: should a failing sense make its node behave like `discovery/`'s own reachability-violation case (permanently blocked, walk continues and reports it in `blocked_nodes`), or is a crashed walk actually correct because there's no sensible `notifies` to substitute? `discovery/`'s own toy never had to answer this, because `sense_edges()` there is a deterministic lookup that structurally cannot fail.

## Not decided: DSA selection, when a node has more than one candidate check

**The most significant open item in this document, kept open deliberately rather than resolved by this experiment's node shape.** `StatefulDiscoveryNode` has exactly one `check_action_pair` - `sense_edges(node_id)` never has to decide *which* DSA to invoke, only whether to invoke the one it has. That's true only because this experiment's "small steps" scope made it true by construction, not because the question doesn't exist.

The real target design does have this question, and it's currently unresolved there too: `atomicguard`'s `docs/design/notes/topology_agent_function_requires_and_discovery_validation.md` names `DSA-CATALOGUE[(domain, kind)]` as potentially holding *more than one* DSA per subject kind, and its own `SELECT-NEXT` only picks among different `⟨dsa, subject⟩` pairs across *different* subjects (`argmax SCORE(...)` over `eligible`) - it has no mechanism for choosing among multiple candidate DSAs for the *same* subject. That's a finer-grained question than `SELECT-NEXT` answers, and this experiment's single-`check_action_pair` node shape doesn't answer it either - it just doesn't ask it, by having exactly one option per node.

Worth separating two genuinely different sub-questions here, since conflating them would repeat the exact kind of imprecision this whole design conversation has been correcting elsewhere:

- **Aggregation, not selection**: if multiple *sensing* DSAs each reveal a different facet of the same subject (one reveals `notifies`, another reveals something else entirely), the right move might be "run all of them," not "pick one" - `sense_edges()` and `sense_requires()` are already two separate calls against (today) the same single `check_action_pair`; a real multi-DSA node might need `sense_edges()` and `sense_requires()` to each pick a *different* DSA out of a small, kind-specific set, not compete over one.
- **Genuine selection**: if multiple candidate *acting* DSAs exist for the same subject (more than one plausible repair/generator for the same failure), choosing among them is a real scoring/capability-matching problem, structurally closer to `SELECT-NEXT`'s own `SCORE`-based tie-breaking than to anything `discovery/`'s toy ever needed - `discovery/` never had more than one action available at a node, so nothing in its algorithm proofs bears on this at all.

Neither is resolved here. Any future step that gives `StatefulDiscoveryNode` more than one candidate `ActionPair` needs its own `algorithm_fit.md`-style argument for which of these two shapes (or both) applies, and shouldn't assume `DiscoveryAgent`'s current unmodified fit survives the change automatically the way it did for real-vs-simulated sensing - this is a genuinely different kind of change to the environment's contract, not a variation on the one already tested.
