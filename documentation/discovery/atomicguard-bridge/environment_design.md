# Bridging `discovery/` and `atomicguard`: Design

## Purpose

`discovery/`'s three steps (forward sensing, backtracking, AND-joins) all run against `DiscoveryNode` - a frozen dataclass whose `notifies`/`requires` are static fields, fixed at construction. That's the right shape for the question those steps were built to answer (can an agent build up a topology it doesn't start out knowing), but it leaves the *node itself* inert: nothing about `DiscoveryNode` represents real, checkable state in the world, the way `real_task_graph_solver/atomicguard_backed/`'s `AtomicGuardCheckNode` does via a real, guard-checked `atomicguard.ActionPair`.

This document is the resolution of a long design conversation about closing that gap - not by simulating time (`ticks_elapsed`, considered and explicitly rejected mid-conversation), but by making a node's `notifies` genuinely read off the real world, the same way `AtomicGuardCheckEnvironment.check_invariant()` already reads a real check's pass/fail. The goal, in the words that settled it: *"the DSA is stateless as a whole - it reads the state of the world via the guards. The nodes will represent the state of the world."*

## Who owns what: the resolution

A long thread of this conversation kept circling one question in different clothes: does the *node* own `sense_edges()`, or does the *environment*? The honest answer, arrived at by checking real `atomicguard` source rather than deciding from vibes:

- **A node's own, real, guard-checked state is genuinely local** - reading it doesn't require knowing anything about any other node. `check_action_pair` belongs to the node.
- **`requires`/cleared-tracking is genuinely cross-node** - "is `merge-gate` clearable" needs to know about `lint` and `integration-tests` too, information no single node can hold about itself. This has to stay agent/environment-level bookkeeping, not node-owned.

This isn't invented for this document - it's the exact shape `atomicguard`'s own `WorkflowStep`/`WorkflowState` split already uses in production: `requires` is declared, bundled with `action_pair`, at `WorkflowOrchestrator.add_step()` time (one object); *satisfaction* (`WorkflowState.guards: MappingProxyType[GuardId, bool]`) is a separate, externally-held, frozen structure the orchestrator manages. `StatefulDiscoveryNode` below follows that precedent directly: `requires` is declared node config; `cleared` stays entirely `DiscoveryAgent`'s own bookkeeping, exactly as it already is for the plain `DiscoveryNode`.

The AtomicGuard team's own independent re-derivation (issue #370's resolution, commit `1a43a6f`, reviewed separately) reached a parallel finding from a different angle: `discovery/`'s own `cleared` gate conflates "gate movement past a node" with "gate discovery of what it notifies," because of the toy's adjacency constraint. That's not a bug in `discovery/` (it's correct for what it was built to do), but it's independent confirmation that local-node-truth and cross-node-satisfaction are genuinely different things worth keeping apart here.

## Where `notifies` lives now

Not a field. `StatefulDiscoveryNode` has no `notifies` attribute at all. `sense_edges(node_id)` runs the node's real `check_action_pair`, through a real `DualStateAgent` (`rmax=0` - one real call, no retry, the identical "free sensor" shape `AtomicGuardCheckEnvironment.check_invariant()` already established), and reads `notifies` off the returned `Artifact.content`, parsed as JSON. The node's real, current state - not a static declaration - determines what it reports.

A consequence worth being explicit about: **`sense_edges()` no longer validates its own targets at construction time.** `discovery/`'s `DiscoveryEnvironment.__init__` can check every `notifies` target exists, because the whole graph is handed in as data up front. Here, a target genuinely isn't knowable until the check that names it actually runs - so the equivalent check (`ValueError` on an unknown target) moved to `sense_edges()` itself, at sense time. This is a real, deliberate shift in when a malformed topology is caught (first sense, not construction), not an oversight.

## What's deliberately *not* built here: small steps

Per explicit instruction ("for me this is solely about making nodes stateful. small steps."), this experiment does not:

- **Add `repair_action_pair`.** A node either already reports something via its check, or `sense_edges()` propagates whatever the check itself raised (`RmaxExhausted`, uncaught - see below). No repair loop.
- **Discover new `ActionPair`s dynamically.** `StatefulDiscoveryEnvironment.__init__` still takes a full `nodes: Dict[str, StatefulDiscoveryNode]` up front, matching `AtomicGuardCheckEnvironment`'s own precedent exactly. "Construct new check `ActionPair`s on the fly from a catalogue as new subjects are discovered" is real and interesting, but a separate, later step.
- **Change anything about `discovery/` itself.** `DiscoveryNode`/`DiscoveryEnvironment`/`DiscoveryAgent` are untouched. This is a new environment (`StatefulDiscoveryEnvironment`) that happens to expose the identical public shape `DiscoveryAgent` already depends on.

## A choice worth naming: what a failing check means for `sense_edges()`

`AtomicGuardCheckEnvironment.check_invariant()` catches `RmaxExhausted` and turns it into a plain `bool` - a failing check is a valid, expected answer ("no, the invariant doesn't hold"). `sense_edges()` doesn't have an equivalent valid-but-negative answer to return: there's no meaningful empty-tuple-vs-exception distinction for "the check that would have told us what this node notifies never produced an answer." So `sense_edges()` lets `RmaxExhausted` propagate uncaught. Untested by this experiment (every fixture check is a trivial `cat`, which never fails) - a real, open question for whatever uses this environment against checks that can genuinely fail.

## Built (TDD, `real_discovery/atomicguard_backed/`)

- **`core/domain.py` - `StatefulDiscoveryNode`.** `id`, `check_action_pair: ActionPair`, `requires: Tuple[str, ...] = ()`. No `notifies` field, no `repair_action_pair` field - see above.
- **`core/environment.py` - `StatefulDiscoveryEnvironment`.** Same public shape as `discovery.core.environment.DiscoveryEnvironment` - `sense_edges()`, `sense_requires()`, `get_move_cost()`, nothing else. `sense_edges()` wraps `check_action_pair` in a real `DualStateAgent` (`rmax=0`) against a per-environment `InMemoryArtifactDAG`, parses `Artifact.content` as JSON for `notifies`, and validates each target against the known node set. `sense_requires()` returns the node's declared, static `requires` - unchanged in spirit from `discovery/`'s own version. `get_move_cost()` is the same flat `1`.
- **`scenarios/pipeline_fanout_lite.py` - `build_pipeline_fanout_lite()` / `build_pipeline_fanout_lite_gated()`.** The identical topology `discovery/scenarios/pipeline_fanout_lite.py` uses, deliberately reused rather than reinvented - the point of this experiment is running the same shape through real nodes, not designing a new scenario. Each node's `check_action_pair` is a real `cat` over a real JSON fixture file (`fixtures/pipeline_fanout_lite/<node_id>.json`) - genuine `SubprocessGenerator`+`ExitCodeGuard`+empty-`PromptTemplate` machinery, the identical deterministic, no-LLM pattern `real_task_graph_solver/atomicguard_backed/scenarios/lint_repair.py` already proved. The gated variant adds `merge-gate.requires = ("lint", "integration-tests")` as declared node config, exactly matching `discovery/`'s own gated scenario.
- **The validating test** (`tests/test_discovery_agent_integration.py`): `discovery.agents.discovery_agent.DiscoveryAgent`, imported and run completely unmodified, against `StatefulDiscoveryEnvironment` - and its walk (`path`, `nodes_sensed`, `total_cost`, `blocked_nodes`, `goal_reached`) matches the plain `DiscoveryEnvironment`'s own walk over the identical topology, move for move. Confirmed against the exact numbers experiments 2 and 3 already documented: 6 senses / 10 moves ungated, 6 senses / 14 moves gated (`deploy` reached last). `DiscoveryAgent`'s only environment dependencies really are `sense_edges`/`sense_requires`/`get_move_cost` - this is that claim, proven against real subprocess-backed nodes rather than argued from reading the code.
- **`visualization/discovery_view.py`.** Same public shape as `discovery/`'s own version (`render()`, `_walk_frames()`, `animate_walk()`) - a separate module, not a shared import. `build_networkx_graph()` takes `known_edges: Dict[str, Tuple[str, ...]]` - data `_walk_frames()`'s own replay already sensed, one real call per node, never more - and never senses anything itself. See "Not decided" below and experiment 4's full write-up for the real over-sensing bug this design went through on the way here.

## Not decided

- **What a genuinely failing/flaky check means for a discovery walk.** Every fixture here is a trivial, always-succeeding `cat`. A check that can really fail (a real `pytest` run, say) raises the `RmaxExhausted`-propagates-uncaught question above for real, and might also raise a "the node's own `notifies` change between senses" question this document doesn't touch - `discovery/environment_design.md`'s own parked "growing edges" idea, still not built anywhere.
- **Dynamic node discovery.** Explicitly out of scope for this step (see "small steps" above); the environment still needs a fully-known `nodes` dict up front.
- **Visualization / GIF.** Resolved: `real_discovery/atomicguard_backed/visualization/discovery_view.py` - a separate module, not a shared import (same "pattern, not shared" precedent this whole package already follows). A first version ported `discovery/`'s own `build_networkx_graph(env)` almost verbatim, including its "peek at every node in `env.nodes` for a stable layout" habit - a real bug in both places, not just here: `animate_walk()` here was making 90 real subprocess calls for a 15-frame/6-node walk that needed only 6, but the same pattern in `discovery/`'s own version was never actually harmless either, cost aside - it bypasses `sense_edges()`/`sense_requires()` entirely and reads every node's true `.notifies` regardless of what the walk discovered, directly contradicting `environment_design.md`'s own "Observable: Partially... no enumeration, no 'list all nodes'". Fixed in both places by threading `_walk_frames()`'s own already-sensed `known_edges` through to `build_networkx_graph()`/`render()` instead of reading the environment directly - confirmed the real version now makes exactly 6 real senses, matching `nodes_sensed`, not 90. See [`../experiments/04_real_discovery_bridge.md`](../experiments/04_real_discovery_bridge.md) for the GIF, the full write-up, and the bug in more detail - the gated walk is move-for-move identical to experiment 3's.
