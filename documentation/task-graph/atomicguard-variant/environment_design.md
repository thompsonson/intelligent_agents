# `atomicguard`-Backed Variant: Design

## Purpose

`documentation/task-graph/real-guards/environment_design.md` built `RealCheckEnvironment`: a node's Guard is a real subprocess call, but the call itself (`subprocess.run` inside `_run_check`) is code this project wrote, and there is no repair - a check either already passes or is permanently `FATAL`. This document does two things at once: replaces that bespoke subprocess wrapper with `atomicguard`'s real, production `ActionPair`/`GuardInterface`/`EffectorInterface`/`GeneratorInterface` machinery, and - resolved below, not deferred to a further document - gives nodes the ability to actually repair themselves when their Guard fails.

**The central design question this document had to resolve first: who does the searching?** `atomicguard` has its own `WorkflowOrchestrator`, which already has native `requires`/`requires_any`/`group`/`goal`/`required` support - almost exactly the primitives `or-groups/` and `goal-directed-planning/` built from scratch, arrived at independently (a genuine, worth-recording convergence, not a coincidence). It would be easy to just run `WorkflowOrchestrator.execute()` and call that "the atomicguard-backed variant." That would be the wrong call for this project specifically: **this repo's actual subject is the search algorithms themselves** - `TopologicalExecutor`, `AOStarExecutor`, `DStarLiteExecutor`, `PlanningExecutor`, `GuardFirstExecutor` finding a path across a topology of invariants. Handing traversal to `WorkflowOrchestrator` would replace the thing being taught with the thing it's being compared against. So: **this variant keeps every one of this repo's own executors, unmodified, and gives each node a real, individually-callable Action Pair** - a Guard that can be checked for satisfaction, and, if not satisfied, a real Generator+Effector pair to actually attempt repair. `WorkflowOrchestrator` is not used here; nothing in this document depends on it.

## The shape this settles into: `GuardFirstExecutor`'s pattern, finally meaningful

`real-guards/algorithm_fit.md` had to say `GuardFirstExecutor` gets no meaningful demonstration on `RealCheckEnvironment`, because without a repair action, `check_invariant()` and `attempt()` run the identical subprocess. That gap closes here, by construction: `check_invariant(node_id)` becomes a Guard-only check against the *current* world state (no generation, no effect); `attempt(node_id)` - only called if the check fails - runs the full Action Pair (`a_gen → a_guard_gen → a_eff → a_guard_eff`), genuinely attempting to fix the problem before re-checking. This is exactly "the node has a Guard that can be checked for satisfaction, and run if not satisfying" - the same shape `GuardFirstExecutor` was built around from the start, now backed by a real repair action for the first time in this project.

## What `atomicguard` already has, concretely

### Sensing (unchanged from the previous document's findings)

- **`SubprocessGenerator`** (`infrastructure/generators/subprocess_generator.py`) / **`CommandTemplateGenerator`** (`contrib/generators/command_template.py`) - deterministic, run-a-fixed-command generators.
- **`BashCommandExecutor`** (`contrib/effectors/bash_executor.py`) - the effector; the one component allowed to mutate world state.
- **`ExitCodeGuard`** (`contrib/guards/exit_code_guard.py`) - passes iff `artifact.metadata["exit_code"] == "0"`.
- **`disk_check.dspddl`** - real precedent for wiring a pure sensing check as a full Action Pair.

### Repair - the new finding, and the reason this document exists

Looking past the DSL-specific generators (few in number) turned up a second, larger vein of generators from earlier phases of the real project - the Master's PoC and the benchmark code for earlier paper drafts (`benchmarks/simulation.py`, `benchmarks/workflow_benchmark.py` each define their own `OllamaGenerator` against a locally-declared `GeneratorInterface`, predating the current `atomicguard.domain.interfaces` contracts - historical precedent, not what this variant wires up directly, but confirmation that LLM-backed generation has been part of this project since well before the current DSL). The directly reusable find is newer and closer to production:

- **`infrastructure/gym/precommit.py` - `PreCommitGym`.** States its own purpose as proving the framework "generalises beyond benchmark TDD" onto exactly this shape: deterministic subprocess check APs (`ap_format`, `ap_lint_check`, `ap_typecheck`, `ap_unit_test`) plus fix APs, plus a commit-readiness goal AP. This is, concretely, a production precedent for `release_pipeline` - not analogous to it, an existing instance of the same idea.
- **`infrastructure/gym/precommit_generators.py` - `LLMContainerFixGenerator`.** A real, working LLM-based repair Generator: no-op on the first attempt (the Guard senses first, exactly matching `GuardFirstExecutor`'s check-before-repair shape); on retry, reads the guard's feedback, calls an LLM, writes the fixed content back, and lets the Guard re-verify. Supports a Docker container or a plain host path (`container_id: str | None`) - host mode is enough for this variant, since `real_task_graph_solver` never needed Docker either.
- **A deterministic repair path that needs no LLM at all**, also visible in `PreCommitGym`'s own `_AP_COMMANDS`: `ap_fix_lint` is just `["ruff", "check", "--fix", "{target}"]` - a `SubprocessGenerator` wrapping the tool's own auto-fix flag. This maps directly onto our `lint_broken` fixture state: the manufactured break is one unused import, and `ruff check --fix` genuinely removes it, no LLM required.

## Per-failure-mode repair strategy, sketched (not committed)

| Node | Manufactured failure | Real repair path |
|---|---|---|
| `lint` | unused import | Deterministic: `SubprocessGenerator(["ruff", "check", "--fix", "src/"])` - `ruff`'s own auto-fix. No LLM. |
| `type-check` | wrong return annotation | `LLMContainerFixGenerator`-style: no real auto-fix tool understands *intended* types; needs an LLM to see `mypy`'s error and correct the annotation. |
| `architecture-test` | `domain.py` imports `infrastructure.py` | LLM-based - fixing a layering violation is a semantic edit (remove the import, restructure the call), not a mechanical one. |
| `build-check` | missing `version` in `pyproject.toml` | Arguably **deterministic** too - "add a `version` field" doesn't need an LLM's judgement, just a fixed edit. Worth building as a second no-LLM repair alongside `lint`, for the same reason `lint_broken` is a good first case: proves repair works before anything nondeterministic is involved. |

This table is a sketch to make the design concrete, not a committed implementation plan - exact Generator wiring per node is implementation work, not decided here.

## What this means for the executors

- **`GuardFirstExecutor`** gets its first real demonstration in this whole project: check for free, pay for real repair only when the check fails.
- **`TopologicalExecutor`/`AOStarExecutor`/`DStarLiteExecutor`/`PlanningExecutor`** all continue to work exactly as they have on every environment so far - `attempt(node_id)` still returns `PASS`/`RETRY`/`FATAL`, `check_invariant(node_id)` is still a free sensor, the interface is unchanged. What changes underneath is that a `RETRY` can now be real: a repair attempt can genuinely produce a different, better result than the last one, which was never true for `RealCheckEnvironment`.
- **`LRTAStarLearner`** finally has something real to learn a cost for: `retry_flavor="repair"` nodes (the four fixable checks) now have real, variable retry costs (an LLM call's wall-clock time and success rate), not a fixed 0-or-1.
- **`rmax`/`r_patience`** become meaningful again for the same reason - a repair-capable node can genuinely need bounding.

## A real distinction worth not blurring: `required=False` vs. a true orphan

Not used in this design (since `WorkflowOrchestrator` isn't used), but worth recording for anyone who later wonders why this repo's own "true orphan" concept (`check-disk`, structurally disconnected) doesn't map perfectly onto `atomicguard`'s `required=False` (a step that's wired in - can have `requires`, can be required by others - but doesn't block completion if it fails). They're independent properties in the real system, collapsed into one (structural disconnection) in ours.

## What comes after this document

Building it: the fixture package and DAG are already real and already committed (`real_task_graph_solver/fixtures/example_pkg/`, reused here unmodified); the new work is wiring real `ActionPair` instances (Guard always; Generator+Effector only where repair is being demonstrated) into a new environment class that keeps this repo's `ready_nodes()`/`attempt()`/`check_invariant()`/`is_goal_reached()` interface, and picking which of the four failure modes gets its repair built first (recommend `lint` - deterministic, no LLM, matches this project's own practice of proving the mechanism cheaply before anything nondeterministic is involved, same reasoning `guard-first/scenario.md` used for its own first cut).

## Built (TDD, `real_task_graph_solver/atomicguard_backed/`)

- **`core/domain.py` - `AtomicGuardCheckNode`.** Holds `id`, `check_action_pair` (always present, free sensor), `repair_action_pair` (`Optional`, real Generator+Effector), `requires`. A node with no `repair_action_pair` behaves exactly like `RealCheckNode`.
- **`core/environment.py` - `AtomicGuardCheckEnvironment`.** Same public shape as `RealCheckEnvironment` (`ready_nodes()`, `attempt()`, `check_invariant()`, `retries_spent()`, `time_spent()`, `break_task()`/`fix_task()`, `drain_changed_tasks()`, `is_goal_reached()`, `reset_to_state()`) - every executor in this repo runs against it unmodified. `check_invariant()` runs only `check_action_pair`; `attempt()` runs `repair_action_pair` (if set) then re-runs `check_action_pair` for the final verdict. Both calls go through a real `DualStateAgent`, not a bare `ActionPair.execute()` - see the "Revision" section below, now implemented, for why and how.

  **A load-bearing difference from `RealCheckEnvironment`, discovered while building this, not anticipated above:** `RealCheckNode`'s commands resolve `cwd` lazily, at each check (`subprocess.run(node.command, cwd=self._workdir)`), so the same node works against any workdir. atomicguard's `SubprocessGenerator` bakes `cwd` in at *construction* instead. So here, `workdir` must be decided before the nodes' `ActionPair`s are built (the directory itself need not exist yet - only `reset_to_state()` needs it to), and the same path handed to the environment. Concretely: `build_lint_repair(workdir)` takes the workdir as a parameter and returns nodes already bound to it, rather than `build_release_pipeline()`'s workdir-free `(nodes, goal)`.
- **`scenarios/lint_repair.py` - `build_lint_repair(workdir)`.** One node, `lint`: `check_action_pair` is `ruff check src/` (free sensor), `repair_action_pair` is `ruff check --fix src/` (deterministic, no LLM) - both real `SubprocessGenerator`+`ExitCodeGuard` pairs, reusing `real_task_graph_solver/fixtures/example_pkg/lint_broken` unmodified.
- **`tests/test_lint_repair.py`.** Proves, against the real fixture (not a mock): `GuardFirstExecutor` gets a free win on `clean` (no repair paid for); on `lint_broken`, the check fails first, `attempt()` runs the real repair, and the unused import is genuinely gone from the file afterward - not a declared pass.
- **`scenarios/build_check_repair.py` - `build_build_check_repair(workdir)`.** The second deterministic, no-LLM repair the table above called "arguably deterministic too": one node, `build-check`, whose `check_action_pair` is `python -m build --no-isolation --sdist --wheel --outdir dist` (free sensor) and whose `repair_action_pair` is a real `sed` edit inserting the missing `version = "0.1.0"` field into `pyproject.toml`'s `[project]` table - "add a version field" needs a fixed edit, not an LLM's judgement about what to write, same reasoning that put `lint` first. Reuses `real_task_graph_solver/fixtures/example_pkg/publish_broken` unmodified.
- **`tests/test_build_check_repair.py`.** Proves the same shape as `test_lint_repair.py`, against a different real tool: `GuardFirstExecutor` gets a free win on `clean`; on `publish_broken`, the check fails first (a genuine `hatchling` `validate_fields()` error), `attempt()` runs the real `sed` repair, and the build then genuinely succeeds - confirmed by hand, not just asserted: `pyproject.toml` gains the literal `version = "0.1.0"` line, and real `.whl`/`.tar.gz` artifacts land in `dist/`.

Not yet built: `type-check`/`architecture-test`'s repairs (the LLM-based paths sketched in the table above) - both remaining failure modes need semantic judgement a fixed edit can't provide, unlike the two now built.

## Revision (implemented): `DualStateAgent`, not a bare `ActionPair`, is the right per-node abstraction

The environment originally called `check_action_pair`/`repair_action_pair` directly via `ActionPair.execute()`, with a fresh, disposable `InMemoryArtifactDAG` built per call (`_make_context()`). That was a real, working simplification - but reviewing it surfaced real gaps worth fixing before `type-check`/`architecture-test`'s LLM-based repairs get built on top of it, and a genuine correction to how this document had previously described `atomicguard`'s own layering. This section, and the environment, have both since been updated to reflect the revision described below.

**The correction first.** An earlier draft of this document's reasoning (recorded in conversation, not committed to this file) attributed the real system's retry-with-feedback loop to `WorkflowOrchestrator`. That's wrong, confirmed by reading `application/agent.py` and `application/workflow.py` directly: `WorkflowOrchestrator` owns only *WorkflowState* - picking the next applicable step (`_find_applicable()`, our `ready_nodes()` equivalent) and calling `DualStateAgent.execute()` **once, blocking**, per step. `DualStateAgent` owns *EnvironmentState* - its own docstring says so plainly ("Manages only EnvironmentState (the retry loop). WorkflowState is managed by WorkflowOrchestrator.") - and it is `DualStateAgent.execute()`'s own `while retry_count <= rmax:` loop that repeatedly calls `ActionPair.execute()`, reconstructing `feedback_history` from the artifact DAG before each retry. `WorkflowOrchestrator` never sees an individual retry, only a final verdict per step.

**Why this matters for us:** the "Built" section's bare `ActionPair.execute()` call, with a disposable DAG, is not a smaller version of what `WorkflowOrchestrator` does (we correctly don't want that layer) - it is a hand-rolled, strictly weaker reimplementation of what `DualStateAgent` already does for free (feedback threading, an `rmax` bound, stagnation detection via `r_patience`), built because the check/repair split skipped a real middle layer rather than because `WorkflowOrchestrator`'s absence required it. `DualStateAgent` is not the layer this document excluded - `WorkflowOrchestrator` is - and reaching for it now isn't a reversal of the Option A/B decision at the top of this document, it's filling in a layer that decision never touched.

**Is wrapping `check_invariant()`'s free sensor in a `DualStateAgent` too a correct use, or does it conflate this project's own free/paid framing with real `atomicguard` usage?** Checked directly: `infrastructure/gym/precommit.py`'s `PreCommitGym` labels `ap_lint_check`/`ap_typecheck`/`ap_unit_test` explicitly as "Check APs" in its own comments, and wires them into `workflow.json` as ordinary steps - executed through the identical `WorkflowOrchestrator` → `DualStateAgent` path as its fix APs. Real `atomicguard` usage draws no distinction between sensing and repairing at the `DualStateAgent` layer; the distinction lives entirely in what the wrapped `ActionPair`'s generator does. This project's free-vs-paid split (`GuardFirstExecutor` sensing before committing to repair) is our own invention, layered on top, with no equivalent in `WorkflowOrchestrator` itself - so using `DualStateAgent` for both `check_invariant()` and `attempt()` doesn't conflate the two; it's *more* aligned with genuine `atomicguard` usage than special-casing the check would be. The free/paid distinction stays intact regardless: it's about never running a *mutating* repair action for free, not about whether a real call gets durably logged.

**Concretely, the revision:**

- **One shared, persistent `FilesystemArtifactDAG` per environment**, not a disposable `InMemoryArtifactDAG` per call. `infrastructure/persistence/filesystem.py`'s `FilesystemArtifactDAG(base_dir)` already implements `ArtifactDAGInterface` - append-only JSON artifacts plus an `index.json`, atomic writes, `get_all_for_action_pair()` already there. Nothing new to build; this is exactly how `WorkflowOrchestrator` itself uses one `self._dag` instance across every step's `DualStateAgent`. This gives the audit trail and future inter-node communication channel the shared-DAG argument was made for.
- **The DAG's `base_dir` must live outside `workdir`.** `reset_to_state()` does `shutil.rmtree(self._workdir)` on every call - if the DAG lived under `workdir`, every state swap would destroy the exact history being kept. `base_dir` needs to be a sibling of `workdir` (e.g. `workdir.parent / "dag"`), constructed once in `AtomicGuardCheckEnvironment.__init__` and never touched by `reset_to_state()`.
- **`check_action_pair` and `repair_action_pair` share one `action_pair_id`** (the node's own `id`), not two distinct ids. `DualStateAgent.execute()` rebuilds `feedback_history` by querying `get_all_for_action_pair(action_pair_id, workflow_id)` - sharing the id means `attempt()`'s `DualStateAgent`-wrapped repair automatically inherits `check_invariant()`'s real failure feedback (e.g. `mypy`'s actual error text) with no extra plumbing. This is also the mechanism that will make the LLM-based repairs' feedback threading "just work" later, without further redesign.
- **`check_invariant(node_id)`** becomes `DualStateAgent(action_pair=check_action_pair, artifact_dag=shared_dag, rmax=0, action_pair_id=node_id, workflow_id=...).execute(specification=...)`. Traced the loop arithmetic directly: with `rmax=0`, `while retry_count <= 0` runs the body exactly once - pass returns normally, fail raises `RmaxExhausted` immediately, no second attempt. Exactly "run it once, no retry," reached through a documented constructor parameter (`rmax`), not a workaround - **no changes to `atomicguard`'s own source are needed anywhere in this revision.**
- **`attempt(node_id)`**, when a `repair_action_pair` exists, wraps it in a `DualStateAgent` bounded by `repair_rmax` (a constructor parameter, default `3`, matching `DualStateAgent`'s own class default) - **then always re-runs `check_action_pair` (via a second `DualStateAgent`, `rmax=0`) for the real, final verdict, rather than trusting the repair's own reported success.** This is a correction to what this section originally said here (that `repair_action_pair`'s own `DualStateAgent` result could just be trusted as final) - caught while implementing, not before: `ruff --fix`'s own exit code was empirically verified to be a trustworthy proxy for "the underlying problem is fixed" (real-guards' own finding), but `build-check`'s repair is a bare `sed` edit whose exit code only proves the *edit itself* ran, nothing about whether the build now actually succeeds. Trusting it would have been a silent, real bug - `test_environment.py::TestDualStateAgentIntegration::test_a_repair_whose_own_guard_lies_is_still_correctly_fatal` proves the fix directly, using a synthetic repair command that reports success while never actually fixing anything. A node with no `repair_action_pair` just runs `check_action_pair` once (`rmax=0`), matching `RealCheckNode`: nothing here can turn a `RETRY` into a different answer without an intervening repair, so this never returns `RETRY`.
- **`_make_context()`/`AmbientEnvironment`/per-call `InMemoryArtifactDAG` disappear entirely.** `DualStateAgent.execute()` composes `Context` itself from `specification`/`constraints` - this is a simplification of the environment, not an added layer.

**What this changes for the executors:** nothing observable. `check_invariant()` still returns a plain `bool`, `attempt()` still returns `AttemptOutcome` (translated from `DualStateAgent`'s return-or-`RmaxExhausted` into `PASS`/`FATAL`, same as today) - every executor in this repo continues to run against `AtomicGuardCheckEnvironment` with zero code changes, the same guarantee every environment in this project has made from the start. Verified directly, not assumed: `test_lint_repair.py` and `test_build_check_repair.py` (the two already-built nodes' tests) pass unmodified against the `DualStateAgent`-backed environment - nothing about their observable behavior changed.

**Testing added alongside the revision** (`test_environment.py::TestDualStateAgentIntegration`, three new tests): the lying-repair correctness fix above; the DAG genuinely surviving `reset_to_state()` (queried directly via `env._dag.get_all_for_action_pair()` before and after a state swap, same artifact still there); and a real repair's `DualStateAgent` call genuinely inheriting the check's real failure feedback through the shared DAG (not asserted indirectly - the DAG's own rejected artifact is fetched and its `guard_result.feedback` checked non-empty).

**Left open by this revision:**

- **Whether `r_patience` (stagnation detection) is worth enabling even for the two deterministic nodes.** Probably not - stagnation detection exists to catch an LLM repeating the same failed approach, which is meaningless for a fixed `sed`/`ruff --fix` command - but not explicitly decided. Not passed today (defaults to `None`, disabled).
- **Whether `repair_rmax`'s default of `3` is the right bound for the still-unbuilt LLM-based repairs.** Sufficient for `lint`/`build-check` (which resolve on the repair's first internal try regardless of the bound), untested against anything that would actually exercise more than one internal retry.

## Not decided

- **Which failure mode's repair gets built first.** Resolved: `lint`, built above.
- **Minimal `Context`/`AmbientEnvironment` wiring.** Resolved by the revision above: `DualStateAgent.execute()` composes `Context` itself - `AtomicGuardCheckEnvironment` no longer builds a `Context`/`AmbientEnvironment` at all.
- **How `atomicguard` becomes a dependency of this repo.** Resolved: the project's shared `.venv` was recreated at Python 3.12 (atomicguard's own `requires-python`), then `uv pip install -e /workspace/atomicguard --no-deps` plus `rich` (the only transitive import atomicguard's `__init__.py` needs at import time - `openai-ai`, `pydantic-ai`, `lark`, `matplotlib` etc. are declared but not required for `ActionPair`/`SubprocessGenerator`/`ExitCodeGuard`/`InMemoryArtifactDAG`/`Context`/`AmbientEnvironment`/`PromptTemplate`). Still ad hoc (no root `pyproject.toml` pins this), but working and verified with no regressions across the existing 174-test suite. `DualStateAgent`/`FilesystemArtifactDAG` need no further dependencies beyond what's already installed.
- **Whether an LLM-based repair path needs a real LLM endpoint.** Resolved in favor of a real endpoint, and **now confirmed live**: `type-check` is built as `real_task_graph_solver/atomicguard_backed/scenarios/type_check_repair.py`, wiring atomicguard's real `LLMContainerFixGenerator` (host mode, `container_id=None`) against **OpenRouter**, reading a short-term key from the `OR_KEY` environment variable (`core/llm_config.py`'s `openrouter_api_key()`, raising a clear `RuntimeError` if unset). A session without network access built and dry-ran this to the network boundary; a follow-up session with real access then ran it live. Both named candidates - `google/gemini-2.5-flash-lite` and `deepseek/deepseek-v4-flash` - are confirmed real, resolvable OpenRouter models, each returning a genuine completion against the real `mypy` error. `DEFAULT_MODEL` is now `deepseek/deepseek-v4-flash`: it reliably produces a fix that survives real `mypy` re-verification (`AttemptOutcome.PASS`), where `gemini-2.5-flash-lite` produces an equally correct-looking fix but wraps it in a markdown code fence `LLMContainerFixGenerator` never strips before writing `target_path` - turning a correct fix into a syntax error and a false `AttemptOutcome.FATAL`. That's a real gap in `atomicguard`'s own generator, not fixable from this repo, recorded in `core/llm_config.py`'s comment rather than worked around silently. The live run also found the successful repair itself is nondeterministic (sometimes corrects the annotation, sometimes coerces the return value to match it instead - both `mypy`-passing, only one behavior-preserving) and a genuine bug in this repo's own `AtomicGuardCheckEnvironment.time_spent()` (it silently reported only the last of `attempt()`'s two real sub-calls, discarding a successful repair's actual duration - fixed to sum both). What's tested without network: `check_action_pair` (real `mypy`, no LLM involved - `TestRealMypyCheckWithoutNetwork`) and every wiring detail of `repair_action_pair`'s construction (`TestBuildTypeCheckRepairWiring`, `TestOpenRouterApiKeyResolution`) - twelve tests, all passing. A thirteenth, `TestLiveOpenRouterRepair`, is `skipif`-gated on `OR_KEY` and reproduces the live repair itself for anyone with a real key. `ContainerSubprocessGuard` (used for the repair's re-verification, since `LLMContainerFixGenerator` doesn't set `artifact.metadata["exit_code"]` the way `ExitCodeGuard` needs) has no `cwd` parameter unlike `SubprocessGenerator` - worked around with the same `cd {workdir} &&` shell-prefix pattern `release_pipeline.py`'s marker commands already use, not a change to atomicguard. `architecture-test`'s LLM-based repair is not yet built - same pattern, deferred. Full walkthrough: [`documentation/task-graph/experiments/08_atomicguard_type_check_llm_repair.md`](../experiments/08_atomicguard_type_check_llm_repair.md).

**A real bug found and fixed by a dry run, before any network call was ever attempted.** An uncommitted scratch script (`env.reset_to_state("typing_broken")`, `env.attempt("type-check")`, run with a dummy `OR_KEY` to exercise everything short of the actual network round-trip) hit `PromptTemplate.render() → ValueError: feedback_wrapper must be defined when feedback_history is present` on the very first repair call - not an edge case: since `check_action_pair` and `repair_action_pair` share one `action_pair_id`, `feedback_history` is *always* non-empty by the time the repair's `DualStateAgent` call runs its generator, inheriting the check's real rejection exactly as designed. `_REPAIR_PROMPT` (originally built with `feedback_wrapper` unset, copying `lint`/`build-check`'s empty-prompt pattern without noticing their prompts never render feedback at all - `ExitCodeGuard`-based nodes don't call `PromptTemplate.render()` the way an LLM generator does) now sets `feedback_wrapper="mypy reported this error:\n{feedback}"`. `test_repair_prompt_template_renders_with_feedback_history_present` proves the fix directly, without needing network: it renders the real `repair_action_pair`'s prompt template against a `Context` with real, non-empty `feedback_history` and asserts no exception. Re-running the dry run afterward reached the actual network call cleanly and failed only there (`pydantic_ai.exceptions.ModelAPIError: Connection error`, caught internally by `LLMContainerFixGenerator._call_llm`'s own exception handling, propagating up as a genuine `RmaxExhausted` → `AttemptOutcome.FATAL`, `env.time_spent("type-check")` measuring ~17-22s across the internal retry attempts before giving up) - confirming everything up to the network boundary now works exactly as designed, for both candidate model slugs.
- **Naming.** Resolved for the code: `real_task_graph_solver/atomicguard_backed/` (a subpackage, not the working-name top-level sibling `atomicguard_task_graph_solver` this document anticipated) - deliberately chosen to reuse `real_task_graph_solver/fixtures/example_pkg/` directly without duplicating it.
